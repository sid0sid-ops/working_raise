# 🛠️ RAISE: Research Assessment Intelligence & Semantic Extraction — Diagnostics & Troubleshooting

This guide provides diagnostic procedures, common error resolutions, and recovery playbooks for operators and developers maintaining the RAISE (Research Assessment Intelligence & Semantic Extraction) backend.

---

## 🩺 1. Quick Diagnostic Checklist

When encountering an issue, execute this 3-step triage:

### Step 1: Run Operator Diagnostics
```bash
python operator_checkup.py
```
This inspects:
- Database connectivity (PostgreSQL, Redis, Neo4j)
- LLM inference responsiveness (vLLM / Ollama)
- ChromaDB vector store health
- Cloudflare Tunnel ingress

### Step 2: Query API Health Endpoint
```bash
curl -i http://localhost:8000/api/health
```
A healthy response returns HTTP 200 with all databases `true`:
```json
{"status": "healthy", "databases": {"postgres": true, "redis": true, "neo4j": true, "vllm": true, "chroma": true}}
```

### Step 3: Check Docker Container Status
```bash
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
```
All 6 containers should show status `Up`:
- `raise-backend`
- `raise-vllm-prod`
- `raise-neo4j-prod`
- `raise-postgres`
- `raise-redis`
- `raise-cloudflared`

## 🔍 2. Common Issues & Resolutions

### Issue 1: "Why does the Cloudflare trycloudflare.com URL look like random words?"
**Symptom**: The Quick Tunnel generates an ephemeral URL like `https://bald-carbon-sleep-moses.trycloudflare.com` instead of a custom phrase like `raise-api`.  
**Technical Cause**: By design, Cloudflare's public testing server (`api.trycloudflare.com/tunnel`) assigns random 4-word subdomains for all anonymous Quick Tunnels to prevent naming collisions and squatting across millions of free users. Cloudflare does not accept custom subdomain requests directly on the shared `*.trycloudflare.com` zone.  

**Resolutions**:
1. **Use the Active Quick Tunnel**: The URL generated by `raise-cloudflared` (currently `https://bald-carbon-sleep-moses.trycloudflare.com`) is fully functional with HTTPS, SSE streaming, and CORS. Simply paste it into the frontend Settings.
2. **Permanent Branded URL Without a Domain (Free Cloudflare Worker)**:
   You do not need to purchase a domain. Free Cloudflare accounts include a free `*.workers.dev` subdomain. A 5-line Worker can route `https://raise-api.<your-subdomain>.workers.dev` to the backend.
3. **Custom Domain (If you own one)**:
   In Cloudflare Zero Trust (**Networks > Tunnels > raise-backend**), add a Public Hostname (e.g. `api.yourdomain.com`) pointing to `raise-backend:8000`.

### Issue 2: vLLM Out-of-Memory (CUDA OOM) or Crash
**Symptom**: `raise-vllm-prod` terminates or logs `torch.cuda.OutOfMemoryError`.  
**Cause**:
- GPU VRAM is under 16 GB, or another process (e.g. gaming, rendering, or Ollama) is consuming VRAM.
- `--gpu-memory-utilization` is set too high.  
**Resolution**:
1. Check GPU memory with `nvidia-smi`.
2. Terminate background processes occupying VRAM.
3. If memory is tight, adjust `--gpu-memory-utilization 0.75` in the vLLM launch arguments.
4. If running without a dedicated 16GB+ GPU, switch to the Ollama CPU/hybrid fallback:
   - In `.env`, set `LLM_BACKEND=ollama`, `LLM_MODEL_NAME=qwen2.5:7b`, `OLLAMA_BASE_URL=http://localhost:11434`.

### Issue 3: Cloudflare Returns HTTP 502 Bad Gateway / 504 Gateway Timeout
**Symptom**: Frontend or curl to `https://*.trycloudflare.com` returns 502 or 504.  
**Cause**: `raise-cloudflared` cannot route traffic to `raise-backend:8000`.  
**Resolution**:
1. Check if `raise-backend` is running:
   ```bash
   docker ps | grep raise-backend
   ```
2. Verify both containers are on the same Docker network:
   ```bash
   docker inspect raise-backend -f '{{json .NetworkSettings.Networks}}'
   docker inspect raise-cloudflared -f '{{json .NetworkSettings.Networks}}'
   ```
   Both must belong to `raise-production_raise-prod-network`.
3. Test direct reachability inside the Docker network:
   ```bash
   docker exec -it raise-cloudflared wget -qO- http://raise-backend:8000/api/health
   ```

---

### Issue 4: Frontend Blocked by CORS
**Symptom**: Browser console displays: `Access to fetch at '...' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present`.  
**Cause**: The frontend origin is not in the allowed origin regex list.  
**Resolution**:
1. Standard GitHub Pages (`https://*.github.io`) and Cloudflare Tunnels (`https://*.trycloudflare.com`) are permitted automatically.
2. If hosting on a custom domain (e.g. `https://research.university.edu`), add it to `CORS_ALLOWED_ORIGINS` in `.env`:
   ```env
   CORS_ALLOWED_ORIGINS=https://research.university.edu,http://localhost:3000
   ```
3. Restart `raise-backend`:
   ```bash
   docker restart raise-backend
   ```

---

### Issue 5: SSE Streaming Hangs or Freezes Mid-Generation
**Symptom**: Chat begins streaming tokens, then freezes or times out during deep graph exploration.  
**Cause**: Proxy buffers the response because SSE content-type headers or keep-alive comments are missing.  
**Resolution**:
- The RAISE backend automatically emits `: keepalive\n\n` comments every few seconds during multi-hop graph hops.
- Verify headers include:
  ```http
  Content-Type: text/event-stream; charset=utf-8
  Cache-Control: no-cache
  X-Accel-Buffering: no
  ```

---

### Issue 6: Neo4j Connection Refused (`bolt://raise-neo4j-prod:7687`)
**Symptom**: Backend logs `Failed to establish connection to bolt://raise-neo4j-prod:7687`.  
**Cause**: Neo4j JVM takes 15–30 seconds to fully initialize the database engine after container start.  
**Resolution**:
1. Check Neo4j startup logs:
   ```bash
   docker logs raise-neo4j-prod 2>&1 | tail -n 20
   ```
   Wait until you see: `Started.` and `Bolt enabled on 0.0.0.0:7687`.
2. Verify Neo4j password in `.env` matches the `NEO4J_AUTH` environment variable used when starting the container.
3. Note: The backend automatically falls back to NetworkX in-memory graphs if Neo4j is temporarily restarting.

---

### Issue 7: Redis Connection Timeout
**Symptom**: Backend logs warning `Redis connection failed. Using in-memory cache.`  
**Cause**: Redis container is stopped or port 6379 is blocked.  
**Resolution**:
- Start Redis: `docker start raise-redis`.
- The system operates without interruption using the internal RAM LRU cache when Redis is offline.

## 📞 3. Getting Further Assistance
If an issue persists after reviewing this guide:
1. Run `python operator_checkup.py --json > checkup.json`.
2. Inspect the latest 100 log lines: `docker logs --tail 100 raise-backend`.
3. Submit an issue on the repository tracker with the sanitized checkup JSON.
